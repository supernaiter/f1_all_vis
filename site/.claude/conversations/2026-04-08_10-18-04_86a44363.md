# autonomous-harness v2.0

## Architecture

```
PM（このエージェント, model: opus）
 │  保持: 北極星 + タスクツリー + 1行サマリのみ
 │  役割: タスク分解 → 派遣 → 判定 → 再計画 → ループ
 │
 ├─→ GENERATOR（サブエージェント, model: sonnet）
 │     入力: 事前契約 + 関連ファイルパス + 制約
 │     出力: RESULT(1文) + FILES_CHANGED
 │     終了後コンテキスト破棄
 │
 ├─→ EVALUATOR（サブエージェント, model: sonnet）
 │     入力: 検証基準 + 成果物パス（実装意図は渡さない）
 │     出力: VERDICT(PASS/FAIL) + EVIDENCE
 │     終了後コンテキスト破棄
 │
 └─→ PM判定:
       PASS → タスクツリー更新 → 次タスク
       FAIL → GENERATOR差し戻し（最大3回）
       3回FAIL → SKIP → 次タスク
       全タスク完了 → 北極星再評価 → 新タスク or REPORT
```

制約: サブエージェントの生成は1階層のみ。GENERATORもEVALUATORもAgentツールを使わない。

## Phase 0: DISCOVER

**ここで人間とのやりとりを全て終わらせる。以降は質問しない。**

```
1. 北極星: 最終的な勝利条件は何か
2. 制約: 時間・技術スタック・既存資産の制約
3. 受け手: 成果物を使うのは誰か
4. 品質の定義: 「できた」の判定基準
5. 既存資産: 流用できるコード・データ
```

原則:
- 1メッセージに詰める。往復最小化
- 「AとBどっち？」形式。自由回答を求めない
- 未回答は最も保守的な仮定で埋める

ゴールテキストが十分明確 or `--skip-discover` → スキップ可。

### 優先順位の判定基準

```
最優先: ブロッカー（これがないと他が全て止まるもの）
次:     リスクが高いもの（失敗したら設計が変わるもの）
後回し: 確実にできるが時間がかかるもの
やらない: 北極星に直接貢献しないもの（明示的に切り捨てる）
```

### 出力テンプレート

```markdown
   - 優先: {最優先/次/後回し}

## やらないこと（省略禁止）

## リスク
- {失敗しそうなポイント} — {検知方法}
```

それ以外 → 承認を待たずに Phase 2 へ。

## Phase 2: EXECUTE（永続ループ）

### 開始時に読む
- `references/generator-contract.md`（GENERATORテンプレート）
- `references/evaluator-contract.md`（EVALUATORテンプレート）

### ループ構造

```
WHILE 北極星 NOT achieved:

  task = 最優先の未完了・非ブロックタスク
  IF タスクなし:
    北極星との距離を再評価
    IF 十分近い → Phase 3 へ
    ELSE → 新タスクを生成して CONTINUE

  ## 1. 事前契約を宣言
  タスクツリーから事前契約を出力:
    作るもの / 制約 / 検証方法(TYPE) / リスク

  ## 2. GENERATOR派遣
  generator-contract.md のテンプレートを読む
  {変数} を埋める:
    - what_to_build: タスクの「作るもの」
    - constraints: 制約 + 北極星の制約
    - relevant_file_paths: Glob/Grepで事前特定
    - working_directory: cwd
    - retry_section: 初回は空
  Agent(model: "sonnet", prompt: 埋めたテンプレート) で派遣
  結果から RESULT と FILES_CHANGED を抽出

  ## 3. EVALUATOR派遣
  evaluator-contract.md のテンプレートを読む
  {変数} を埋める:
    - verification_criteria: タスクの検証基準
    - verification_type: TYPE A/B/C/D
    - type_specific_instructions: タイプ別セクションから取得
    - artifact_paths_or_commands: GENERATORの FILES_CHANGED + 補足
  Agent(model: "sonnet", prompt: 埋めたテンプレート) で派遣
  結果から VERDICT と EVIDENCE と SUMMARY を抽出

  ## 4. PM判定
  IF VERDICT == PASS:
    task.status = PASS
    task.summary = GENERATORのRESULT（1文）
    タスクツリーを再評価:
      - 不要になったタスクを削除
      - ブロック解除されたタスクを更新
      - 新たに必要になったタスクを追加
  ELSE (FAIL):
    task.retries += 1
    IF retries >= 3:
      task.status = SKIP
      task.summary = "SKIP: " + EVALUATORのSUMMARY
      ブロックされるタスクがあればマーク
    ELSE:
      EVALUATORのEVIDENCEをリトライセクションに設定
      同じタスクでGENERATOR再派遣 → EVALUATOR再派遣 → 再判定
```

### 実行中の原則
- 人間に質問しない
- 判断に迷ったら最も保守的な選択
- 想定外の事態はログに記録、Phase 3 でまとめて報告
- 前タスクのFAILが後タスクをブロックする場合のみ停止

## レビュー結果

### 1. `scripts/openf1_client.py` — OpenF1クライアント

**良い点:**
- QPS制限・リトライ・バックオフが堅牢
- etl.common依存を完全にインライン化
- フォールバックカラム検索が防御的

**問題点:**
- **L66 jitterの計算がバグ**: `0.5 - time.time() % 1` は `-0.5〜+0.5` になる。結果として `need + (jitter * negative)` で待ち時間が短縮され、QPS超過しうる。`random.uniform(0, jitter)` にすべき
- **L84 resp.json()のエラーハンドリングなし**: 200でもレスポンスボディが壊れている場合にJSONDecodeErrorで落ちる
- **fetchメソッド群の大半は未使用**: `fetch_team_radio`, `fetch_pit_events`, `fetch_intervals`, `fetch_laps_openf1`, `fetch_rcm_openf1`, `fetch_stints`, `fetch_weather`, `fetch_car_data`, `fetch_location` — card_generatorでは使われていない。元のetlコピーの残骸。25KBのうち半分以上が死にコード

### 2. `scripts/openf1_card_generator.py` — カード生成

**良い点:**
- コーナー自動検出が実用的（speed極小値+最小間隔フィルタ）
- 3分窓で25%地点を使う設計は妥当
- 上位10ドライバー限定でAPI負荷を抑制

**問題点:**
- **L37 GP_DIR_MAPがR01-R03ハードコード**: R04以降を追加するたびに手動修正が必要。`data/`ディレクトリをスキャンする動的解決のほうが保守性が高い
- **L329-332 コーナー対応付けが脆弱**: 各ドライバーの`own_corners`を`corners`（reference driver）のインデックス順で1:1マッピングしている。しかしドライバーごとにコーナー検出数が異なると、T5がreference driverのT7に対応する等のズレが起きる。GPS座標の最近傍マッチングで対応付けすべき
- **L207 overtake検出ロジックが粗い**: position入れ替わり検出が「同じpositionにいた人」の線形検索。DRS圏外でポジションスワップが起きた場合（ピットストップ由来）もオーバーテイクとして記録される。lapベースフィルタが必要
- **L117-122 nearest_xyが線形検索**: 小さいデータなので問題ないが、`bisect`で高速化可能

### 3. `site/src/pages/cards/[gp]/[card].astro` — Canvas描画

**良い点:**
- 7カード種を1テンプレートで処理、cardType分岐が明確
- `fitOutline`の座標正規化が正しい
- pending判定が複合条件で堅牢

- **L146-184 braking-point描画**: ブレーキ開始点が全ドライバーのリングを同じコーナー座標中心に重ねている。10ドライバー×20コーナーで最大200リングが同心円状に積み重なり、視認性が極めて低い。角度方向にドライバーごとにオフセットすべき
- **L226-239 corner-speed**: `d.color + '15'`で半透明にしているが、これはhex colorが`#RRGGBB`の場合のみ有効（`#RRGGBBAA`になる）。color-mixと不整合

### 優先順位の判定基準

```
最優先: ブロッカー（これがないと他が全て止まるもの）
次:     リスクが高いもの（失敗したら設計が変わるもの）
後回し: 確実にできるが時間がかかるもの
やらない: 北極星に直接貢献しないもの（明示的に切り捨てる）
```

## Phase 2: EXECUTE（永続ループ）

### 開始時に読む
- `references/generator-contract.md`（GENERATORテンプレート）
- `references/evaluator-contract.md`（EVALUATORテンプレート）

### ループ構造

```
WHILE 北極星 NOT achieved:

  task = 最優先の未完了・非ブロックタスク
  IF タスクなし:
    北極星との距離を再評価
    IF 十分近い → Phase 3 へ
    ELSE → 新タスクを生成して CONTINUE

  ## 1. 事前契約を宣言
  タスクツリーから事前契約を出力:
    作るもの / 制約 / 検証方法(TYPE) / リスク

  ## 2. GENERATOR派遣
  generator-contract.md のテンプレートを読む
  {変数} を埋める:
    - what_to_build: タスクの「作るもの」
    - constraints: 制約 + 北極星の制約
    - relevant_file_paths: Glob/Grepで事前特定
    - working_directory: cwd
    - retry_section: 初回は空
  Agent(model: "sonnet", prompt: 埋めたテンプレート) で派遣
  結果から RESULT と FILES_CHANGED を抽出

  ## 3. EVALUATOR派遣
  evaluator-contract.md のテンプレートを読む
  {変数} を埋める:
    - verification_criteria: タスクの検証基準
    - verification_type: TYPE A/B/C/D
    - type_specific_instructions: タイプ別セクションから取得
    - artifact_paths_or_commands: GENERATORの FILES_CHANGED + 補足
  Agent(model: "sonnet", prompt: 埋めたテンプレート) で派遣
  結果から VERDICT と EVIDENCE と SUMMARY を抽出

  ## 4. PM判定
  IF VERDICT == PASS:
    task.status = PASS
    task.summary = GENERATORのRESULT（1文）
    タスクツリーを再評価:
      - 不要になったタスクを削除
      - ブロック解除されたタスクを更新
      - 新たに必要になったタスクを追加
  ELSE (FAIL):
    task.retries += 1
    IF retries >= 3:
      task.status = SKIP
      task.summary = "SKIP: " + EVALUATORのSUMMARY
      ブロックされるタスクがあればマーク
    ELSE:
      EVALUATORのEVIDENCEをリトライセクションに設定
      同じタスクでGENERATOR再派遣 → EVALUATOR再派遣 → 再判定
```

### 実行中の原則
- 人間に質問しない
- 判断に迷ったら最も保守的な選択
- 想定外の事態はログに記録、Phase 3 でまとめて報告
- 前タスクのFAILが後タスクをブロックする場合のみ停止

## Graphiti × Motorsports-Visualised 適合性分析

### Graphitiとは（要約）
- Zepが開発したOSS（Apache 2.0）の**時間軸付きナレッジグラフ**フレームワーク
- LLMでエンティティ・関係性を抽出 → Neo4j等に格納
- 「AliceはQ1にチームリーダーだったが、Q2からBobに交代」のような**事実の変遷**を追跡
- 主な用途: AIエージェントの長期記憶、会話コンテキスト管理

### 現在のプロジェクトデータ構造
- 純JSON（142MB, 6,372ファイル）、DB不使用
- エンティティ: ドライバー(30名)、チーム(11)、サーキット、レース(R01-R03)
- 関係: ドライバー↔チーム、ドライバーペア(437)、トリプル(1,542)、H2H比較
- パイプライン: Python → JSON → Astro静的ビルド

### 適合性判定: **合わない**

| 観点 | 評価 | 理由 |
|------|------|------|
| **データ特性** | ❌ | プロジェクトのデータは**高度に構造化済み**（ラップタイム、セクタータイム、テレメトリ）。Graphitiは非構造テキストからの関係抽出が強み。既に構造化されたデータにLLMを通す意味がない |
| **時間軸の粒度** | ❌ | Graphitiの時間軸は「事実の変遷」（チーム移籍等）。F1データの時間軸は「ラップ単位のテレメトリ」。粒度が全く違う |
| **コスト** | ❌ | エピソード投入ごとに**複数回のLLM APIコール**。R01-R03で数千ラップ×22ドライバー = 数万エピソード。API費用が爆発する |
| **クエリパターン** | ❌ | 現在のユースケースは「VER vs HAMのセクター3速度差」等の**数値比較**。グラフトラバーサル（「誰の元チームメイトが今誰と同チームか」）は求められていない |
| **インフラ** | ❌ | Neo4j（またはFalkorDB/Kuzu）の運用が必要。現在JSONのみで6,470ページを13秒でビルドできている。複雑性が増すだけ |

### もし合うケースがあるとすれば

唯一の適合点は**AIエージェント層を追加する場合**:

> 「2026年のVERの予選パフォーマンスはどう推移している？チームメイトTSUとの比較で、前年のPER時代と傾向は変わった？」

このような自然言語クエリにAIエージェントが答える対話型機能を作るなら、Graphitiの時間軸ナレッジグラフは有効。ただし現状のpSEO静的サイト戦略とは方向性が異なる。

### 代替案（本プロジェクトに合うもの）

| 方法 | 適合度 | 内容 |
|------|--------|------|
| **SQLite + FTS5** | ★★★★★ | 既存gp_weekend.dbを拡張。全文検索+リレーショナルクエリ。インフラ追加なし |
| **DuckDB** | ★★★★ | JSON/Parquetを直接クエリ。分析クエリが高速。Pythonから使いやすい |
| **手動グラフJSON** | ★★★ | driver_relations.json等でチーム移籍・チームメイト関係を明示定義。LLM不要 |
| **Cognee** | ★★ | Graphiti類似だがシンプル。構造化データにも対応。ただしLLMコスト問題は同じ |

### 結論

**Graphitiは導入しない。** 現在の「構造化データ → JSON → 静的サイト」パイプラインに対して、LLM依存のグラフ抽出は過剰であり、コスト・複雑性が見合わない。
